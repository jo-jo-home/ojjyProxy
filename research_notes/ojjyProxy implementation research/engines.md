# ojjyProxy engine implementation research: Scramjet and Ultraviolet

Research date: 2026-10-12. Research only; no application implementation or runtime testing. Web sources were retrieved during this session. Local ZIPs were inspected in memory with Python `zipfile`; originals were not modified and nothing was extracted. A ZIP citation below means the named member inside that archive, not a claim that the archive equals today's upstream commit.

## 1. Which engine/version should ojjyProxy target, and what do the archives actually contain?

### Takeaway
Use Scramjet as the primary engine, but explicitly choose between the npm-latest **1.1.0 / all-bundle / Bare-Mux** generation and the separately published **2.0.67-alpha.2 / controller / direct-transport** generation. Current upstream main and the supplied main archive use the latter; the TitaniumNetwork Scramjet setup page still teaches the former. Ultraviolet **3.2.10** is an optional legacy engine, with upstream explicitly stating it is unmaintained. [Scramjet registry latest][sj-npm]; [2.x registry][sj-alpha]; [controller registry][controller-npm]; [Scramjet docs][sj-docs]; [UV docs][uv-docs]

### Cited Findings

#### Current upstream and published-package facts

- The core manifest on main is **2.0.67-alpha.2**. That exact version exists on npm, depends on `@mercuryworkshop/proxy-transports 1.0.2`, and exports regular, bundled and bundled-WASM module entry points. Main's package is in `packages/core`, not the repository root. [Main manifest][sj-core]; [published alpha][sj-alpha]
- `@mercuryworkshop/scramjet-controller` npm latest is **0.0.14**; its published development dependency is exactly Scramjet **2.0.67-alpha.2**, although its peer dependency is merely `*`. The runtime assertion requires exact core version equality, and requires core to be loaded before controller. Thus the permissive peer range is not a compatibility promise. - `@mercuryworkshop/proxy-bootstrap` npm latest is **0.0.5**. Its published dev metadata names controller **0.0.13**, whereas the inspected main bootstrap source dynamically chooses a controller from major zero and fetches the core version in that controller's metadata. Do not assume published bootstrap and today's source behave identically. [Published bootstrap][bootstrap-npm]; [main bootstrap server][bootstrap-server]
- Ultraviolet npm latest is **3.2.10**. Both GitHub and TitaniumNetwork say it is superseded/unmaintained; the docs additionally say they will not provide further UV support. UV's old supported-site lists and “regular updates” feature text are historical/promotional statements, not current test results. [UV registry][uv-npm]; [UV upstream][uv-repo]; [UV docs][uv-docs]
- The Scramjet setup page still shows `scramjet.all.js`, `$scramjetLoadController()`, `$scramjetLoadWorker()`, and Bare-Mux. Its linked “Using Transports” page now discourages Bare-Mux because of SharedWorker/message-port lifetime issues and recommends individual transports. These pages are inconsistent across API generations. [Scramjet docs][sj-docs]; [transport guide][transport-docs]
- The docs' floating CI URL names `mercuryworkshop-scramjet-1.0.2-dev.tgz`, describes less extensive testing, and advises `pnpm cache delete @mercuryworkshop/scramjet` before reinstalling another CI build. The availability/content of that floating asset was not checked; it is not evidence that it supplies 2.x. [CI and upgrade sections][sj-docs]

### Inferences
- **Recommendation:** design the new site's engine adapter around the 2.x controller/frame model if the objective is to follow current upstream. Pin the verified **core 2.0.67-alpha.2 + controller 0.0.14** pair, serve matching assets, and validate the alpha in the intended browsers/sites. If selecting 1.1.0 for its documented package-latest path, explicitly record that choice rather than accidentally mixing generations. [Core registry][sj-alpha]; [controller registry][controller-npm]; [version guard][sj-version]
- Retain UV only if a specific target site's testing demonstrates value. The primary-source maintenance status supports Scramjet-first, but does not prove Scramjet faster or universally compatible. [UV upstream][uv-repo]; [SJ upstream][sj-repo]
- Do not use URL codecs as evidence of encryption/privacy: the supplied UV config uses XOR and Scramjet defaults use URI encoding. The UV docs' broad “full end-to-end encryption” wording was not substantiated by the examined engine configuration. [UV snapshot config][zip-uv]; [SJ legacy controller][zip-legacy]; [UV docs][uv-docs]

- No npm tarball file-content inspection, CI release download, or Typedoc crawl was performed. Registry metadata and live repository source are separately identified; neither proves every deployed asset is identical to main. [SJ registry][sj-alpha]; [bootstrap registry][bootstrap-npm]; [docs Typedoc link][sj-docs]

## 2. What setup, assets, builds and configuration are required?

### Takeaway
Separate the **rewriting engine**, **browser transport**, and **network backend**. Source ZIPs need builds; published packages provide distributions. Scramjet 2.x needs a matching controller/core pair and direct transport; Scramjet 1.x and UV 3.x use Bare-Mux in the examined configurations. [SJ source/build README][sj-repo]; [2.x controller source][sj-controller]; [1.x metadata][sj-npm]; [UV metadata][uv-npm]

### Cited Findings

#### Scramjet 2.x: actionable current-source setup
1. **Select matched artifacts.** An explicit package selection is `@mercuryworkshop/scramjet@2.0.67-alpha.2` and `@mercuryworkshop/scramjet-controller@0.0.14`; select a direct transport version compatible with the `ProxyTransport` interface. The verified controller metadata names `proxy-transports 1.0.2`. [Core registry][sj-alpha]; [controller registry][controller-npm]
2. **Asset map.** Current controller defaults require core JS `/scramjet/scramjet.js`, controller injection JS `/controller/controller.inject.js`, real WASM `/scramjet/scramjet.wasm`, plus its API and SW bundles. The virtual `scramjet.wasm.js` is generated within frame routes; it is not the real WASM file. Bootstrap maps the core to `/scram/scramjet.js` and `/scram/scramjet.wasm`, so configure paths consistently rather than assuming these route examples are interchangeable. [Controller defaults/virtual response][sj-controller]; [bootstrap defaults][bootstrap-common]; [bootstrap asset routes][bootstrap-server]
3. **Worker entry.** Serve a classic SW that imports the controller SW bundle, tests `$scramjetController.shouldRoute(event)`, and calls `event.respondWith($scramjetController.route(event))` only for relevant requests. The main demo and captured website use precisely this pattern; nonmatching requests are left to ordinary browser handling. [Main demo snapshot `packages/demo/public/sw.js`][zip-main]; [website `/sw.js`][zip-site]; [bootstrap-generated entry][bootstrap-server]
4. **Frontend sequence.** Register/activate the SW, load core before controller API, initialize a direct transport, construct `new Controller({ serviceworker, transport, config, scramjetConfig })`, then await `controller.wait()` before creating/navigating a frame. Use `controller.createFrame(iframe)` and `frame.go(absoluteTargetUrl)`; controller/frame prefixes are internally generated. `config` controls route/assets/codec; `scramjetConfig` controls core rewriting behavior. [Controller implementation][sj-controller]; [bootstrap initialization][bootstrap-client]; [version guard][sj-version]
5. **Transport/backend.** Bootstrap's client resolves Wisp as `ws(s)://<same-host><wispPath>` and creates `LibcurlTransport.LibcurlClient({ wisp })` or `EpoxyTransport.EpoxyClient({ wisp })`. The new direct transport constructors differ from Bare-Mux's `setTransport(modulePath, args)` interface. Bootstrap's `bare` branch explicitly throws “Bare transport not implemented yet.” [Client source][bootstrap-client]
6. **Bootstrap option.** Main's starter server calls `await bootstrap()`, checks `routeRequest(req,res)` before `express.static('public')`, and connects `server.on('upgrade', routeUpgrade)`. Starter frontend invokes `initBootstrap()` and creates a controller frame. This is an upstream reference, not a tested turnkey deployment in this research. [Starter server][starter-server]; [starter frontend][starter-client]
7. **Defaults and operational requirements.** Main bootstrap defaults to **libcurl**, `/sw.js`, `/wisp/`, and generated `/bootstrap-init.js`. Its server downloads npm tarballs into a writable `.downloads` directory and implements Wisp WebSocket upgrade handling. Thus its startup requires registry access and writable storage, rather than merely copying a frontend ZIP to a static host. [Default config][bootstrap-common]; [server downloads/upgrade routing][bootstrap-server]

#### Current-source bootstrap/controller caveats worth resolving before implementation
- Bootstrap config types advertise version pin fields such as `scramjetVersionPin` and `scramjetControllerVersionPin`, but the inspected `server.ts` does not use them when selecting/downloading packages. Installing bootstrap itself at an exact version does not, by itself, freeze the packages it retrieves dynamically. [Config types][bootstrap-common]; [selection implementation][bootstrap-server]
- The server's inspected `routeRequest` asset table includes the libcurl client, but **does not include the configured epoxy client path**, even though the client tries to load it when `transport: 'epoxy'`. This is a source-level discrepancy; an additional server route/static mechanism would be needed unless the published package differs. [Server asset table][bootstrap-server]; [client loading][bootstrap-client]
- `routeUpgrade` checks the literal `/wisp/` prefix rather than reading `config.wispPath`, while the browser uses the configured path. Changing only that option appears insufficient in this source. [Server upgrade handler][bootstrap-server]; [client Wisp resolution][bootstrap-client]
- Bootstrap's `loadRest()` returns the controller without awaiting `controller.wait()`. The controller's `createFrame()` checks the presence of its Promise, not whether it has resolved. Add an explicit wait in the consuming setup to avoid assuming readiness from construction alone. [Bootstrap client][bootstrap-client]; [controller readiness][sj-controller]
- Current controller persists cookies in origin-wide IndexedDB `__scramjet_controller` and synchronizes through a fixed BroadcastChannel name. Per-frame route prefixes do not imply per-frame cookie jars; the controller owns a shared jar. [Controller source][sj-controller]

#### Building the supplied Scramjet main source
- Upstream instructions: recursive clone, `pnpm i` at root, then in `packages/core` run `pnpm rewriter:build` and `pnpm build`; `pnpm dev` at root serves the demo on `localhost:4141` and does not rebuild the Rust rewriter on every source change. ZIP use lacks git commit metadata, so cloning a pinned commit is preferable for reproducibility. [README][sj-repo]; [main source snapshot][zip-main]
- The supplied root pins package manager **pnpm 10.12.1** and enforces pnpm via a preinstall script. Source uses workspace/catalog dependencies; do not independently install only `packages/core` as if it were an isolated npm source tree. [Root/package manifests and workspace][zip-main]
- The inspected rewriter requires Cargo/rustup, Rust **nightly**, `rust-src`, `wasm32-unknown-unknown`, **wasm-bindgen-cli 0.2.105**, Binaryen `wasm-opt`, and the `r58Playz/wasm-snip` fork. `build.sh` explicitly rejects a different wasm-bindgen version and copies output to `dist/scramjet.wasm`. These are build-time prerequisites; using published built packages avoids compiling the Rust rewriter locally. [ZIP members `packages/core/rewriter/wasm/build.sh`, `rust-toolchain.toml`, `.github/actions/setup-rewriter-toolchain/action.yml`][zip-main]; [README dependency list][sj-repo]
- “Recent Node” is the README's requirement, not an exact supported Node minimum. Root dev commands execute `.ts` directly, and bootstrap uses `import.meta.dirname`; select a modern Node release that supports the inspected tooling rather than inferring a minimum from the publisher's `_nodeVersion`. [README][sj-repo]; [root manifest][zip-main]; [bootstrap server][bootstrap-server]

#### Scramjet 1.1.0: documented old-generation path
- Install exact `@mercuryworkshop/scramjet@1.1.0` using pnpm. Expose package distribution via `import { scramjetPath } from '@mercuryworkshop/scramjet/path'`. Serve `/scram/scramjet.all.js`, `/scram/scramjet.wasm.wasm`, `/scram/scramjet.sync.js` from the same build. The repeated `.wasm.wasm` name belongs to this generation; current 2.x uses `scramjet.wasm`. [Docs][sj-docs]; [1.1.0 snapshot config/exports][zip-legacy]
- Frontend loads Bare-Mux and the selected compatible transport plus `scramjet.all.js`, obtains `ScramjetController` through `$scramjetLoadController()`, passes prefix/assets/codec/flags configuration, and initializes it. Await `scramjet.init()` because it writes config to IndexedDB; the docs' unawaited example omits that sequencing detail. Initialize/await Bare-Mux transport before navigation. [Docs][sj-docs]; [legacy controller init][zip-legacy]
- Worker imports `scramjet.all.js`, gets `ScramjetServiceWorker` via `$scramjetLoadWorker()`, awaits `loadConfig()`, uses `route(event)` then `fetch(event)`, and falls back to native fetch. **Fix the documentation sample:** it currently passes an async function to `respondWith` instead of invoking it or passing a Response Promise. The supplied legacy `static/sw.js` correctly passes `handleRequest(event)`. [Docs sample][sj-docs]; [correct snapshot worker][zip-legacy]
- The scramgel source needs its original separate bundles and global controller API; replacing only its SW import with an all-bundle example is not a complete migration. Both scramgel and legacy demo SWs contain a Firefox `crossOriginIsolated` override expressly labeled “please dont do this in prod.” That override does not create actual browser isolation and should not be copied as deployment configuration. [scramgel worker/controller/bundler][zip-scramgel]; [legacy worker][zip-legacy]

#### Ultraviolet 3.2.10 setup
- Install `@titaniumnetwork-dev/ultraviolet@3.2.10`, or build the source with dependency installation then `npm run build`. The source `build.js` copies `src/sw.js` and `src/uv.config.js` to `dist/` and bundles **uv.bundle.js, uv.client.js, uv.handler.js, uv.sw.js**. `lib/index.cjs` exports `uvPath`, the server filesystem path to `dist`. Source builds are JS/esbuild-based, without Scramjet's Rust/WASM rewriter toolchain. [Build/install docs][uv-docs]; [snapshot build/path helper][zip-uv]
- Mount the UV assets consistently, for example `/uv/`. Edit `self.__uv$config` so `prefix` is a distinct proxy route such as `/service/uv/`, and `handler`, `client`, `bundle`, `config`, `sw` are absolute `/uv/...` asset URLs. The provided default config assumes root asset URLs, not `/uv/`; moving the files alone breaks those references. [Snapshot `src/uv.config.js`][zip-uv]
- In both page and worker contexts, load **uv.bundle.js before uv.config.js** because config accesses `Ultraviolet.codec`. The worker then imports the configured `uv.sw.js`, constructs `UVServiceWorker`, dispatches `uv.route(event)`/`uv.fetch(event)`, and uses native fetch otherwise. The registration wrapper `sw.js` and engine bundle `uv.sw.js` are different files. [Current stock worker][uv-sw-entry]; [docs import-order notes][uv-docs]
- For navigation, form the route using the selected config prefix plus that config's `encodeUrl(absoluteTargetUrl)`; use its matching decoder to display/unpack the URL. The supplied config uses `Ultraviolet.codec.xor`. Keep the frontend and SW using the same config. [Snapshot config][zip-uv]; [engine route/sourceUrl use][uv-sw]
- UV 3.x's `BareClient` is backed by Bare-Mux. Provide its browser worker/transport assets, initialize a compatible Bare-Mux connection/transport and backend before navigation. A Wisp transport is not the same thing as a legacy Bare server, and UV's older “Bare server v3+” migration text should not be treated as a universal requirement for every UV 3 transport. [UV package dependencies][uv-npm]; [UV worker][uv-sw]; [UV 3.0.0 changelog/docs][uv-docs]

### Inferences
- Suggested first implementation sequence: choose/pin engine generation → inventory actual package output → map JS/WASM/SW URLs → make a working direct transport and Wisp upgrade route → verify SW activation → initialize/wait controller → navigate one frame → add UI/optional UV. Each step addresses a dependency visible in current source; this is an engineering sequence, not a verified working app. [Bootstrap source][bootstrap-server]; [client sequence][bootstrap-client]; [controller][sj-controller]
- For a production-oriented 2.x setup, manually serving a locked matched artifact set is more reproducible than relying on the inspected bootstrap's dynamic latest-in-major selection and unused pin options. [Bootstrap version selection][bootstrap-server]; [pin declarations][bootstrap-common]
- Serve real JS/WASM with appropriate MIME types, and exclude these asset routes from SPA HTML fallbacks. Bootstrap explicitly emits `application/javascript` and `application/wasm`; SW registration requires valid JavaScript MIME. [Server MIME handling][bootstrap-server]; [MDN registration][mdn-sw]

### Gaps
- The bootstrap discrepancies are source-verified, not reproduced runtime failures; published 0.0.5 could differ. Validate published code or use a deliberately explicit setup before adopting the helper. [Published metadata][bootstrap-npm]; [current source][bootstrap-server]
- Exact compatible transport package pins for a manually assembled deployment were not tested. Bootstrap currently selects Epoxy major **3** or libcurl major **2**; do not transplant 1.x Bare-Mux argument examples into those direct constructors. [Major constants][bootstrap-common]; [constructor usage][bootstrap-client]
- No hosting environment, CSP, cross-origin-isolation feature requirements, target-browser matrix or Wisp capacity was specified/tested. In particular, real COOP/COEP requirements should be checked for the chosen transport/features; the archived Firefox flag override is not evidence that isolation is optional. [Archived demo override][zip-legacy]; [current controller isolation parameter][sj-controller]

## 3. How should service-worker scope, routing and engine switching work?

### Takeaway
The SW registration **scope**, engine **proxied-URL prefix**, and engine **asset directory** are separate settings. Prefer one root dispatcher SW for the new site's controller-based Scramjet path; if UV is retained, give it a distinct route prefix and explicitly dispatch to its engine. Engine switching should reconstruct navigation from the canonical target URL, not replace SW registrations or reuse another engine's encoded URL. [MDN scope rules][mdn-sw]; [SJ routing][sj-controller]; [UV routing][uv-sw]

### Cited Findings
- SW registration requires a secure/trustworthy origin (HTTPS or localhost) and a same-origin SW URL/scope; default scope is the SW script's directory. A broader scope requires `Service-Worker-Allowed` on the SW script response plus the requested registration scope. Root `/sw.js` avoids needing that header for `/`. [MDN][mdn-sw]
- Registration scope controls documents/clients, not just an `if pathname` test. Setting `prefix: '/service/'` in engine config does not make `/assets/sw.js` control `/service/` documents. Root-level asset routes such as `/scram/` do not have to equal the proxied document prefix. [MDN scope description][mdn-sw]; [UV config versus route implementation][uv-sw]; [controller config][sj-controller]
- A unique scope has one registration; re-registering another script at that scope updates the registration. With overlapping registrations, the most specific matching scope controls the document, and only one SW runs for it. Thus two engines do not independently intercept the same document by both registering scope `/`. [MDN][mdn-sw]
- Current Scramjet Controller builds its prefix as configured base + random controller ID + `/`, then each Frame adds a random frame ID. Requests must find the associated live controller reference and frame; routing is an RPC bridge back to the controlling page. [Controller prefix/frame logic][sj-controller]; [SW references/routing][sj-controller-sw]
- Current SW calls `skipWaiting()` and `clients.claim()`, and sends a revival message when restarted; the controller re-establishes its MessageChannel. This differs from the 1.x IndexedDB `loadConfig()` SW model. [Current SW][sj-controller-sw]; [current controller][sj-controller]; [legacy snapshot][zip-legacy]
- Bootstrap registers a **classic** SW with `updateViaCache: 'none'`, waits for readiness/activation and returns a SW reference. That cache option applies to SW scripts/imports, not every engine asset fetched by the app. [Helper][bootstrap-clientcommon]; [MDN cache-option definition][mdn-sw]
- UV's route test is `request.url.startsWith(location.origin + config.prefix)`; it only fetches/rewrites matching proxied URLs and normally fetches nonmatching URLs. Scramjet's new SW predicate checks registered controller prefixes. Both support selective routing, but those checks use different API/state models. [UV][uv-sw]; [SJ SW][sj-controller-sw]
- Current Scramjet `controller.setTransport(transport)` updates existing frame fetch handlers. That is **transport switching within Scramjet**, not switching the rewriting engine to UV. Older generations use Bare-Mux `setTransport`; again, this is not a Scramjet/UV engine toggle. [Controller method][sj-controller]; [old docs][sj-docs]

### Inferences

#### Recommended routing design
1. **Root dispatcher:** use a single `/sw.js`, scope `/`, with classic-script imports appropriate to the pinned generation. Load current Scramjet controller SW; if UV is present, load UV bundle/config/SW in order. In one fetch listener, route to Scramjet if its predicate matches, otherwise UV if its prefix matches, otherwise native fetch (or leave the event unhandled). Ensure there is exactly one selected `respondWith` path. This composition is supported by the examined predicates but was not executed here. [SJ predicate][sj-controller-sw]; [UV stock wrapper][uv-sw-entry]; [MDN scope][mdn-sw]
2. **Separate namespaces:** use, for example, Scramjet base `/~/sj/`, UV prefix `/service/uv/`, core assets `/scram/`, controller assets `/controller/`, UV assets `/uv/`, Wisp `/wisp/`. These are proposed application conventions, not mandated names. Include trailing slashes so prefix matching cannot unintentionally include a sibling path. [Current SJ defaults][sj-controller]; [bootstrap defaults][bootstrap-common]; [UV prefix matcher][uv-sw]
3. **Avoid accidentally competing workers:** do not independently register old UV stock SW and Scramjet demo SW at `/`. Separate nonoverlapping scopes can work for independent entry pages, but the new controller's parent-page readiness and messaging make one root dispatcher simpler to reason about. [MDN registration selection][mdn-sw]; [SJ channel initialization][sj-controller]

#### Engine-switching contract for the future frontend
- Keep tab state as `{ engine, targetUrl }`, with `targetUrl` a normalized absolute real URL. Store selected engine independently of route encoding. On **SJ 2.x**, create/use a controller frame and call `frame.go(targetUrl)`; on **UV**, navigate to `uvConfig.prefix + uvConfig.encodeUrl(targetUrl)`. For SJ 1.x use that generation's controller/frame methods, not the 2.x API. This adapter is a proposed design grounded in the differing navigation mechanisms. [SJ frame implementation][sj-controller]; [UV config][zip-uv]; [legacy controller][zip-legacy]
- Switch engines by navigating/recreating the appropriate iframe from the canonical target URL after the selected engine/transport is ready. Do not pass a `/~/sj/<controller>/<frame>/...` route into UV encoding, or treat a UV XOR route as Scramjet's real target URL. Per-controller/frame URLs contain stateful routing identities. [SJ prefixes and frame routing][sj-controller]; [UV decoding use][uv-sw]
- Do not promise cross-engine cookie, storage or history continuity. The examined engines maintain their own cookie machinery; SJ 2.x uses `__scramjet_controller`, SJ 1.x `$scramjet`, and UV opens its own cookie DB API. A proxy engine switch is a new navigation, not a transfer of sessions between those stores. [SJ 2.x persistence][sj-controller]; [SJ 1.x persistence][zip-legacy]; [UV cookies][uv-sw]
- Plan update handling for a matched bundle set, imported SW scripts and active tabs. `updateViaCache: 'none'` helps SW imports, but cannot make mismatched core/controller builds compatible or clear unrelated HTTP-cached JS/WASM. [MDN cache semantics][mdn-sw]; [version assertion][sj-version]

#### Focused future verification checklist
This is suggested validation work for implementation, not tests run in this research: verify all mapped assets return their expected MIME/content (not HTML); clean-profile first navigation and existing-profile upgrade; active SW and correct route predicates; configured Wisp WebSocket upgrade; controller wait/handshake; engine toggle preserves real target URL; ordinary frontend requests bypass engines; restart/revival with multiple tabs; engine-specific redirects, relative assets, POST, cookies, downloads, workers, WebSockets and media. These cases follow observable initialization/routing branches and the unverified compatibility claims. [Bootstrap/client branches][bootstrap-client]; [SW revival][sj-controller-sw]; [UV request handling][uv-sw]; [claimed SJ sites][sj-repo]

### Gaps
- The combined dispatcher is an architectural recommendation; no upstream dual-engine sample or local runtime proof was established. Verify imported bundle globals/listeners cooperate in the exact pinned distributions. [Examined stock UV wrapper][uv-sw-entry]; [examined SJ worker][sj-controller-sw]
- Direct reload/bookmark portability of 2.x frame routes was not tested. Because routing references are live and prefixes include random IDs, persist/reopen the real target URL through the frontend rather than assuming an encoded frame URL is a durable standalone link. [Controller IDs/frame lookup][sj-controller]; [SW tab references][sj-controller-sw]
- No evidence establishes transparent migration of cookies/storage between engines. Browser bugs discussed in transport docs were not independently reproduced or checked against specific stable browser versions. [Engine persistence][sj-controller]; [UV cookies][uv-sw]; [Bare-Mux caveat][transport-docs]
