# Engine demos, frontend UX and interaction states for ojjyProxy

Research date: 2026-10-12. This pass covers the supplied Scramjet website capture, Scramjet main/scramgel/legacy demos, the official Scramjet-App and Ultraviolet-App frontends, and the engine code needed to explain their behavior. Source inspection only: no running demo, browser compatibility test, application code, or archive modification. ZIP members were read in memory. Pair these notes with `engines.md` for versions, builds and scope; other site inventories should be synthesized separately by the report writer.

## 1. What user-facing features do the actual demonstrations implement?

### Takeaway
The captured Scramjet site is a **developer-oriented browser demo** with Browser, Requests, Playground and Settings panels; the official UV and Scramjet-App frontends are much simpler URL/search launchers. Useful combined features are URL/search navigation, frame back/forward/reload, real-URL tracking, escaped-link recovery, transport configuration, a request inspector and a locally saved rewriter playground. Engine choice, automatic failover, isolated private browsing tabs and robust reconnect UI are proposed additions, not observed demo features. [Captured bundle][sitezip]; [main demo source][mainzip]; [UV frontend][uv-index]; [SJ-App frontend][sj-index]

#### Implemented-looking controls that should not be overstated
- Playground back/forward icon buttons have **no click handlers**; preview reload invokes `goPreview(storedPreviewUrl)` rather than calling native frame reload on its currently navigated URL. These exact unwired buttons also occur in the captured bundle. [Main ZIP `Playground.tsx` preview toolbar][mainzip]; [capture `omnibox-nav` buttons][sitezip]
- Browser navigation's “or search” label is unsupported by its normalization implementation. It also changes saved `homeUrl` on every submit, conflating a home preference with last typed navigation. A richer omnibox is new frontend work. [BrowserView source][browser-source]
- Request capture installs once after first opening Requests and is not detached when the panel is hidden. Clearing the list is not pausing capture. Only the Browser frame is instrumented by this viewer; the separate playground frame is not “all requests from the whole application.” [Main ZIP `RequestViewer.tsx`, `initPlugin`, `activeSignal`][mainzip]
- Site information text claims “all traffic ... fully end-to-end encrypted.” Settings allow arbitrary URLs and switching transport; HTTP destinations do not acquire destination TLS simply because Wisp uses WSS. Treat that homepage wording as a claim to qualify, not final privacy copy. [Main ZIP `homepage.html`, `SettingsPage.tsx`][mainzip]; [libcurl HTTPS/TLS description][curl-readme]; [Wisp CONNECT format][wisp-spec]

#### Official example frontends
- **Ultraviolet-App**: branded logo/description, URL/search form with hidden Google template `https://www.google.com/search?q=%s`, errors/details placeholders, footer/community/GitHub/Credits links, and a initially hidden iframe. On submit it registers `/uv/sw.js`, initializes Epoxy via Bare-Mux using same-host `/wisp/`, displays the iframe and assigns `__uv$config.prefix + encodeUrl(realUrl)`. That heuristic defaults bare domains to **HTTP**, accepts URL schemes recognized by `URL`, and has no explicit HTTP/HTTPS allow-list; it should be revised for a new site's intended address policy. [Search implementation][uv-search]

A rejected `setTransport` is not given a dedicated user-facing error here. [Frontend][uv-index]; [SW helper][uv-register]
- UV 404 page offers **Register ServiceWorker** for a URL within the configured proxy prefix, then reloads after registration; its text calls this “service worker is not registered.” This is a repair affordance, but a missing registration is not the only possible cause of a route failure. [404 page][uv-404]; [handler][uv-error]
- UV-App server supplies public assets first, then UV/Epoxy/Bare-Mux vendor assets, enables COOP `same-origin` and COEP `require-corp`, and handles `/wisp/` upgrades. Root frontend can be outside `/uv/` worker scope while its `/uv/service/` iframe is inside it. No REST `/navigate` endpoint exists in this example. [Server][uv-server]; [worker helper][uv-register]; [config][uv-config]

Its current main frontend still uses **1.x** `$scramjetLoadController`, all-bundle assets and Bare-Mux libcurl, not the captured 2.x API. Each submit creates/appends another frame with id `sj-frame`; it does not remove/reuse the prior one in this code. It shares the same simple `search()` architecture; the README now points ongoing work toward browser.js. [HTML][sj-html]; [frontend][sj-index]; [README][sj-app]
- Current core's **create-proxy-app starter** is a distinct, newer reference: `initBootstrap()`, a controller frame, HTTP-cache plugin, URL watcher, escaped-link plugin, frame URL label and error text/stack display. Its `navigate()` only normalizes with `https://`, and its catch sees synchronous/init errors rather than all asynchronous frame fetch failures. [Starter frontend][starter]
- **browser.js** README calls itself a configurable browser-in-browser and advertises embedding/headless/cloud-browser uses. This pass did not inventory its UI source, so do not infer bookmarks, tabs, engine failover or settings from that README alone. [Official repository][browserjs]

## 2. Which capabilities belong to the engine, and what are the browser/privacy/session limits?

### Takeaway
HTML/CSS/JS and header rewriting, cookie emulation, storage namespacing, worker rewriting and WebSocket bridging are engine/transport work. Search, browser chrome, panels, logs, progress and failover policy are frontend work. The engines emulate a web environment inside the proxy origin; they do not automatically reproduce native browser security boundaries, private-session isolation or continuity across engines. [SJ engine source][mainzip]; [UV engine source][uvzip]; [controller source][controller]

#### Concrete implementation limits, not generic disclaimers
- SJ WebSocket emulation returns `bufferedAmount = 0`; protocol/extensions are initialized as empty strings in this inspected implementation. Source-level semantics deserve compatibility testing for applications depending on flow-control/negotiated properties. WebSocket existence is not proof that every realtime application works. [Main ZIP `client/shared/requests/websocket.ts`][mainzip]
- SJ storage emulation is not a clean native-origin implementation: localStorage uses host (not full scheme/origin); `clear()` loops with `for ... in Object_keys(...)`, which iterates array indexes rather than storage keys; `key(index)` returns a value rather than the expected key. These are code-level discrepancies, not reproduced exploit/bug claims. A report should say “namespaced/emulated storage,” not “verified complete origin isolation.” [Main ZIP `client/dom/storage.ts`][mainzip]
- SJ response-header handling's SameSite/registrable-domain helper uses a simplified last-two-label calculation rather than a full PSL. This can differ for domains such as `example.co.uk`. The cache source labels itself “RFC-9111-ish”, omits 304 revalidation, treats `s-maxage` like `max-age`, and short-circuits with `immutable`. Do not present cookie/cache emulation as fully spec-verified. [Main ZIP `fetch/headers.ts`, `utils/src/http-cache-plugin.ts`][mainzip]
- Body inspector stream mode calls `.tee()` then awaits `.text()` or `.blob()` in the response hook. An infinite/long-lived stream could keep that hook pending and consume unbounded memory; the display's “Load full contents” is not a buffering safeguard. Row limit does not cap body bytes. Source creates media object URLs, but no revoke operation was found in viewer clear/eviction handlers. [Main ZIP `RequestViewer.tsx`, `readStreamBody`, `readStreamBlob`, `clear`][mainzip]
- Request timing is `performance.now()` at request hook to response hook, not full page load, TCP timing, TLS timing or every byte downloaded. Failed requests have no explicit error finalization in that viewer's three capture hooks and may remain pending-looking. [Main ZIP `RequestViewer.tsx`][mainzip]
- UV-App README specifically warns about Firefox deployment/TLS and recommends Chromium for localhost testing; current Scramjet demo has its own SW timeout/revival mechanics. These are version/setup caveats, not a tested declaration that one browser is universally supported/unsupported. Engine browser support must be assessed with SW, WASM, transport and intended sites together. [UV README][uv-app]; [SJ demo initialization][mainzip]; [prior source analysis](engines.md)
- Input normalization for Wisp adds `ws://` if scheme is omitted, even in the captured HTTPS-oriented build. The newer starter instead derives WS/WSS from page protocol. A final UI should validate its actual secure endpoint policy and error clearly rather than blindly reusing the demo normalizer. [Demo `store.ts`][mainzip]; [captured settings bundle][sitezip]; [bootstrap client source][bootstrap-client]

#### Honest privacy and session behavior
- libcurl.js implements destination-side TLS in the browser for **HTTPS** and states the relay cannot read encrypted request contents. Wisp CONNECT nevertheless sends **destination hostname and port** to the relay, and Wisp routes data streams. The inference is encrypted HTTPS payloads do not mean destination metadata is hidden; HTTP/WS destinations do not get HTTPS/WSS encryption automatically. [libcurl README][curl-readme]; [Wisp specification][wisp-spec]
- A frontend that renders/re-writes decrypted content and a request inspector can read that content locally. Captured request headers/body previews may include cookies, authorization tokens, personal data and request URLs. The inspected viewer has no sensitive-field redaction or privacy mode in its render/capture pipeline. A self-hosted frontend/third-party scripts remain part of the trust boundary even when relay TLS is end-to-end. [RequestViewer capture/header render pipeline][mainzip]; [legacy third-party scripts][legacyzip]; [libcurl TLS design][curl-readme]
- Cookie persistence lives in the browser's proxy-origin storage. Closing one frame, hiding a panel, changing Wisp, changing transport, clearing request rows or busting cache does not by itself delete the persisted cookie DB/site stores. “Private tab” or “fresh account container” would require explicit different storage namespaces/jars and verified cleanup. [Controller persistence][controller]; [flag cache action and settings][mainzip]; [UV cookies][uvzip]
- SJ and UV have different cookie DBs/namespaces. An engine switch does not migrate authenticated cookies, in-memory app state, storage or forms. Visiting the same site via two engines may result in two sessions. Changing a Wisp endpoint within the same engine keeps browser-managed engine state but may change destination-observed egress; the examples do not promise login continuity. [SJ controller][controller]; [UV DB/handler][uvzip]; [Wisp creates relay sockets][wisp-spec]
- The fake-origin playground intercepts only local matching GET/HEAD. External resources and other methods use transport, so “local playground” does not mean “offline/no outbound requests.” Its fake `location` is engine emulation, not a genuine browser security origin or SSL certificate for the entered hostname. [Main ZIP `Playground.tsx`, request hook][mainzip]; [SJ logical origin override][mainzip]

### Inferences
- Suggested final-product copy: **“Browse through Scramjet (UV legacy optional). Site cookies and storage are kept in this browser under the proxy site; clearing logs does not sign you out. HTTPS content can use browser-to-destination TLS with a compatible transport, while the relay still sees connection metadata. Engine changes may require signing in again.”** This is proposed explanatory wording, not a verified deployment policy; actual logging/retention/transport settings must determine final copy. [Controller][controller]; [UV namespaces][uvzip]; [TLS][curl-readme]; [Wisp metadata][wisp-spec]
- Separate controls for **Clear request log**, **Clear proxy response cache**, **Reset site/engine session**, and **Reset preferences/playground projects**. Session reset should report exactly which jars/stores were cleared and which tabs are affected; do not equate any existing Clear/Bust button with all four operations. [RequestViewer/FlagEditor/store/Playground implementations][mainzip]; [cookie persistence][controller]
- Keep stream/body capture explicitly enabled, bounded and cancellable in any adapted inspector; impose per-body/total byte budgets and revoke preview URLs on eviction. Those safeguards are new work motivated by the inspected pipeline, not existing demo features. [RequestViewer implementation][mainzip]

- No empirical isolation audit, leak test, WebRTC/DRM/permission/camera/clipboard parity test or per-site login test was performed. Source-level virtual origins and WebSockets do not establish those properties. [Examined engine code][mainzip]; [UV source][uvzip]
- Server-side logging, retention, authentication and privacy policy for the captured third-party Wisp were not established. Do not claim “no logs”, anonymity, hidden client identity, account separation or relay invisibility. [Captured endpoint default][sitezip]; [Wisp connection metadata][wisp-spec]

## 3. What precise UI-to-engine/backend states should the final project specify?

### Takeaway
Track **engine readiness**, **relay/transport health** and **per-tab navigation** separately. A controller constructor, an SW registration, an iframe `load`, a Wisp WebSocket opening, or an HTTP 200 alone does not establish that the requested site is functional. Engine failover/reconnect are application policies to build around source hooks, not capabilities automatically delivered by the demos. [Demo initialization][mainzip]; [controller routing/readiness][controller]; [UV startup][uv-index]; [Wisp handshake][wisp-spec]

### Cited Findings
- New SJ `Frame.go()` rewrites a URL then assigns `element.src`; it returns no document-success promise. Frame error hooks can observe fetch failure and provide a replacement response; controller SW catches exceptions and generates an HTTP 500 response. Therefore `await frame.go()` in an application does not await remote page success. [Controller implementation][controller]; [controller SW source][controller-sw]; [starter use][starter]
- Frame initialization hooks identify `isTopLevel`; URL-watcher comments distinguish actual frame initialization from URL/history/hash changes. These are available evidence signals for an adapter, unlike assumptions from a generic iframe load alone. [Main ZIP `controller/src/types.d.ts`, `utils/src/url-watcher.ts`][mainzip]
- Transport changes apply to new requests in the demo. Underlying libcurl documentation says changing websocket proxy URL does not close existing connections. Source provides no promise that an established application WebSocket migrates seamlessly to another endpoint. [Demo SettingsPage][mainzip]; [libcurl transport-change docs][curl-readme]
- Wisp 2.x separates socket open from INFO/CONTINUE/auth/extension negotiation and specifies close reasons for unreachable/refused/timed-out destinations, blocked/throttled streams, incompatible extensions and authentication failures. These can support differentiated errors only if the selected transport exposes them; the inspected frontend does not wire them to such a UI. [Wisp handshake/close reason specification][wisp-spec]; [existing frontend behavior][mainzip]

### Inferences

#### Proposed state/data contract (new application design)
Maintain a site-level engine adapter state and per-browsing-tab state; these are application models to implement, not upstream types:

- **Engine state:** `uninitialized → loading-assets → registering-sw → awaiting-control → initializing-controller → ready`, with `unsupported` and `failed` exits. Record engine version/controller version, selected transport, configured endpoint, failure stage and retryable reason. Readiness must include the applicable generation's config/handshake, not only registration. [SJ init][mainzip]; [controller version/readiness research](engines.md); [UV registration helper][uv-register]
- **Transport health:** `unknown | connecting | ready | degraded | reconnecting | failed`. “Configured” is not “connected.” Use actual transport/Wisp negotiation signals if exposed; otherwise label an intentional probe result or the last real request outcome accurately. Never infer relay health from the static homepage's availability. [Wisp handshake][wisp-spec]; [demo getTransport/SettingsPage][mainzip]
- **Tab record:** `tabId`, requested engine (`scramjet | ultraviolet | auto`), effective engine, transport/endpoint identity, `inputDraft`, `requestedTargetUrl`, `committedTargetUrl`, `displayUrl`, `navigationId`, phase, engine/frame reference, shell history policy and last structured error. `auto` is explicitly new policy, not an observed engine value. Keep generated proxy routes out of the canonical URL fields. [Different SJ/UV navigation][controller]; [UV frontend encoding][uv-index]
- **Navigation phases:** `idle | waiting-for-engine | navigating | initialized | loaded | degraded | stalled | failed | switching-engine`. Attach monotonically increasing `navigationId` to host-adapter events; stale outcomes from superseded frame generations must not rewrite the current address/error state. Hooks are available, but event correlation is application work. [Request and frame init hooks][mainzip]; [stateful controller frame lookup][controller]

#### Proposed browser-to-backend responsibilities
- **Browser/frontend:** normalization/search; frame/engine lifecycle; real-URL display/history; feature panel preferences; decoder/encoder pairing; retry/fallback policy; request/error hooks; local session/cache/log actions. These map to the inspected handlers and do not need a server to own every navigation. [UV JS][uv-index]; [SJ controller/demo][controller]
- **Static/app server:** deliver pinned assets and SW at configured scopes with proper MIME/headers; serve shell and error routes; route Wisp upgrades to relay implementation. Source examples have no shared browser profile database, tab history database, or engine-choice REST API. Add any persistence service only as an explicitly new feature. [UV server][uv-server]; [current bootstrap source/setup](engines.md)
- **Wisp/transport:** relay connection lifecycle and destination stream outcomes; transport-side TLS for compatible HTTPS/WSS; connection metadata/error reasons. It is not the HTML rewriter or the UI's tab manager. If the transport obscures raw Wisp reasons, UI must fall back to “transport request failed,” not invent DNS/auth-specific explanations. [Wisp specification][wisp-spec]; [libcurl design][curl-readme]

### Gaps
- Adapter event shape, HTTP status/error bridging from UV into the shell, reconnect API, abort/stop support and browser-history boundary detection require implementation-specific investigation. Proposed application states should not be presented as existing upstream exported APIs. [Examined Frame methods][controller]; [UV frontend][uv-index]
- Correctly classifying “engine-specific failure” is not solved by these demos. Fallback heuristics need target-site testing and must account for remote valid error pages, pages loading but throwing script errors, cookies/auth and partial resource failure. [Existing capture/error hooks][mainzip]; [UV SW handling][uv-sw]
- Old/demo feature flags are version-sensitive. Final explanation should use pinned-generation names and explicitly state which features are shipped, experimental, proposed or unsupported. See `engines.md` for the verified generation mismatch. [Flags/types][mainzip]; [engine notes](engines.md)
