## 1. What is actually in the current hub repository, and what constrains integration?

### Takeaway

The hub is a custom TypeScript `Deno.serve()` server rendering HTML strings, with Deno KV-backed accounts/sessions and local-first, GitHub-fallback game assets. Its existing root-scoped offline worker, authentication gate, HTML injection, and asset exclusion configuration make a proxy more than a drop-in static folder. [Server](https://github.com/jo-jo-home/ojjys-game-hub/blob/91be48dcf75dbe7d1771eab9aa90b1b233c1a033/server.ts); [worker](https://github.com/jo-jo-home/ojjys-game-hub/blob/91be48dcf75dbe7d1771eab9aa90b1b233c1a033/public/sw.js); [configuration](https://github.com/jo-jo-home/ojjys-game-hub/blob/91be48dcf75dbe7d1771eab9aa90b1b233c1a033/deno.json).

### Cited Findings

#### Framework and deployment configuration — verified source facts

- `server.ts:1–8` imports std `serveDir`, `npm:chess.js@0.10.3`, local account/access/feedback/statistics modules, and public JSON catalogues. `server.ts:1670` starts `Deno.serve(async (req: Request) => ...)`. This is a hand-written server and router; the inspected tree contains no root `package.json`, Next/Fresh/Vite framework configuration, README, or `.github` workflow directory. It does contain `deno.json`, `deno.lock`, TypeScript modules/tests, generator scripts, and a large `public/` tree. [Server L1–8](https://github.com/jo-jo-home/ojjys-game-hub/blob/91be48dcf75dbe7d1771eab9aa90b1b233c1a033/server.ts#L1-L8); [server entry L1670](https://github.com/jo-jo-home/ojjys-game-hub/blob/91be48dcf75dbe7d1771eab9aa90b1b233c1a033/server.ts#L1670); [complete tree API](https://api.github.com/repos/jo-jo-home/ojjys-game-hub/git/trees/91be48dcf75dbe7d1771eab9aa90b1b233c1a033?recursive=1).
- `deno.json:1–10` enables unstable KV, defines `start` as `deno run --allow-net --allow-read --allow-env --unstable-kv server.ts`, and has `deploy.project: "ojjys-game-hub"` plus `deploy.entrypoint: "server.ts"`. Its long `deploy.exclude` list omits game directories and all of `public/apps` from that configured upload. Those exclusions are source configuration, not evidence that the current dashboard build honors them. [deno.json](https://github.com/jo-jo-home/ojjys-game-hub/blob/91be48dcf75dbe7d1771eab9aa90b1b233c1a033/deno.json).
- KV is opened lazily using `Deno.openKv()` (`server.ts:421–424`). Session cookies are host cookies with `Path=/; HttpOnly; SameSite=None; Secure`; sessions persist in KV, and a query token supports the existing about:blank launcher context. [KV/session code](https://github.com/jo-jo-home/ojjys-game-hub/blob/91be48dcf75dbe7d1771eab9aa90b1b233c1a033/server.ts#L421-L450); [login token explanation L1721–1733](https://github.com/jo-jo-home/ojjys-game-hub/blob/91be48dcf75dbe7d1771eab9aa90b1b233c1a033/server.ts#L1721-L1733).

#### Actual routes and ordering — verified source facts

- The handler first applies an environment-controlled lockout (`TYLER_BLOCK`, through `tylerBlocked()`); its 503 page can override all routes. `/login` handles POST authentication and GET rendering. The public offline-file allowlist and public icon handlers then run before the general authentication gate. [Handler L1670–1797](https://github.com/jo-jo-home/ojjys-game-hub/blob/91be48dcf75dbe7d1771eab9aa90b1b233c1a033/server.ts#L1670-L1797).
- The server has explicit API branches for play tracking, feedback, account/profiles/admin/access/session/logout/offline metadata, and a substantial `/api/ojjychess/*` API. These branches precede the catch-all gate and implement their own checks where appropriate; their placement does not imply that all APIs are public. [API router L1803–2720](https://github.com/jo-jo-home/ojjys-game-hub/blob/91be48dcf75dbe7d1771eab9aa90b1b233c1a033/server.ts#L1803-L2720).
- `server.ts:2722–2728` redirects unauthenticated remaining requests to `/login`. Authenticated generated pages include `/feedback`, `/apps`, `/hub`, `/people`, `/profile`, `/account`, and `/me`; `/api/me` appears after this gate. `/` and `/index.html` render a launcher with about:blank and normal `/hub?token=...` links. [Page routes L2722–2815](https://github.com/jo-jo-home/ojjys-game-hub/blob/91be48dcf75dbe7d1771eab9aa90b1b233c1a033/server.ts#L2722-L2815).
- Remaining requests go through `serveDir(req, { fsRoot: "public" })`. On local 404, the server fetches `https://raw.githubusercontent.com/jo-jo-home/ojjys-game-hub/master/public` plus the requested path, appending `index.html` for a trailing slash. HTML responses are modified by `injectGameHead`; successful GitHub non-HTML responses get an inferred MIME type and `public, max-age=86400`. This is fixed-repository asset fallback, not a browser forward-proxy backend. [Fallback L2817–2868](https://github.com/jo-jo-home/ojjys-game-hub/blob/91be48dcf75dbe7d1771eab9aa90b1b233c1a033/server.ts#L2817-L2868); [upstream/MIME L10–25](https://github.com/jo-jo-home/ojjys-game-hub/blob/91be48dcf75dbe7d1771eab9aa90b1b233c1a033/server.ts#L10-L25).

#### Headers and assets — verified source facts

- The common HTML headers are `Referrer-Policy: no-referrer` and `X-Content-Type-Options: nosniff`; generated and injected HTML generally uses `Cache-Control: no-store`. The inspected server has no application-defined global COOP, COEP, CSP, or `Service-Worker-Allowed` policy. This describes source behavior, not measured production headers from an ingress/CDN. [HTML_HEADERS L110–116](https://github.com/jo-jo-home/ojjys-game-hub/blob/91be48dcf75dbe7d1771eab9aa90b1b233c1a033/server.ts#L110-L116); [HTML handling L2831–2853](https://github.com/jo-jo-home/ojjys-game-hub/blob/91be48dcf75dbe7d1771eab9aa90b1b233c1a033/server.ts#L2831-L2853).
- `/sw.js`, offline/session/cloak/theme/profile/catalogue scripts and styles, manifests, and PWA icons are explicitly served from disk before auth, with proper MIME types, `Cache-Control: no-cache`, SHA-1-derived ETags, and conditional 304 responses. Catalog icons get separate caching: hashed WebP paths are immutable for one year; other icons cache for one day. [Public file allowlist L27–59](https://github.com/jo-jo-home/ojjys-game-hub/blob/91be48dcf75dbe7d1771eab9aa90b1b233c1a033/server.ts#L27-L59); [public file/icon handlers](https://github.com/jo-jo-home/ojjys-game-hub/blob/91be48dcf75dbe7d1771eab9aa90b1b233c1a033/server.ts#L1751-L1797).
- MIME mapping already includes `.wasm` as `application/wasm` and `.js` as JavaScript, but omits `.mjs` in the explicit GitHub fallback map; missing extensions default to `application/octet-stream`. A libcurl transport served via fallback as `/libcurl/index.mjs` would therefore need an explicit module MIME mapping. Local `serveDir` MIME handling is a separate path. [MIME definitions](https://github.com/jo-jo-home/ojjys-game-hub/blob/91be48dcf75dbe7d1771eab9aa90b1b233c1a033/server.ts#L13-L25); [getMime](https://github.com/jo-jo-home/ojjys-game-hub/blob/91be48dcf75dbe7d1771eab9aa90b1b233c1a033/server.ts#L103-L106); [upstream transport reference](https://github.com/MercuryWorkshop/Scramjet-App/blob/f6f83cbc93091e47b9c357eb00ea289828aedf94/public/index.js).
- `injectGameHead()` inserts anti-inspect/cloak and game-specific head content into generic static HTML. Consequently, letting proxy shell HTML reach this generic handler would also modify it. [Injection L910–918](https://github.com/jo-jo-home/ojjys-game-hub/blob/91be48dcf75dbe7d1771eab9aa90b1b233c1a033/server.ts#L910-L918); [generic handlers](https://github.com/jo-jo-home/ojjys-game-hub/blob/91be48dcf75dbe7d1771eab9aa90b1b233c1a033/server.ts#L2817-L2853).

#### Service workers and offline behavior — verified source facts

- `public/offline.js` registers `navigator.serviceWorker.register("/sw.js")` on window load. `public/sw.js` is therefore root-scoped by default. The PWA manifest separately specifies `start_url: "/hub"`, `scope: "/"`, and `display: "standalone"`; PWA scope and worker scope are separate concepts. [offline.js](https://github.com/jo-jo-home/ojjys-game-hub/blob/91be48dcf75dbe7d1771eab9aa90b1b233c1a033/public/offline.js); [manifest](https://github.com/jo-jo-home/ojjys-game-hub/blob/91be48dcf75dbe7d1771eab9aa90b1b233c1a033/public/manifest.webmanifest); [scope semantics](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerContainer/register).
- Current worker caches are `hub-shell-v9` and `hub-games-v1`. Activation deletes only obsolete `hub-*` caches, preserves the game cache, and calls `clients.claim()`. Navigation is network-first with cache fallback; game assets can be cache-first; shell cache lookup ignores the query string. Worker fetch handling excludes non-GET/cross-origin traffic, selected live pages, `/api/*`, and `/sw.js`. It currently does not exclude a prospective `/proxy/` namespace. [Worker L13–42, L96–135, L248–272](https://github.com/jo-jo-home/ojjys-game-hub/blob/91be48dcf75dbe7d1771eab9aa90b1b233c1a033/public/sw.js).
- Game/app offline downloads fetch GitHub assets at a resolved commit SHA, rebuild their MIME types, and write to `hub-games-v1`. Ordinary runtime GitHub fallback instead references moving `master`. Proxy dependencies should not depend on that mismatch or be classified as downloadable arbitrary target websites. [offline downloader](https://github.com/jo-jo-home/ojjys-game-hub/blob/91be48dcf75dbe7d1771eab9aa90b1b233c1a033/public/offline.js); [server revision helper](https://github.com/jo-jo-home/ojjys-game-hub/blob/91be48dcf75dbe7d1771eab9aa90b1b233c1a033/server.ts#L78-L101); [runtime fallback](https://github.com/jo-jo-home/ojjys-game-hub/blob/91be48dcf75dbe7d1771eab9aa90b1b233c1a033/server.ts#L2817-L2842).
- The complete tree also contains nested workers for games/apps, including `public/apps/turbowarp/sw.js`, `public/apps/windows11/{sw.js,serviceWorker.js}`, `public/breaklock/service-worker.js`, and several game `sw.js` files. Their presence is verified; their individual registrations and production activity were not audited. [Complete tree](https://api.github.com/repos/jo-jo-home/ojjys-game-hub/git/trees/91be48dcf75dbe7d1771eab9aa90b1b233c1a033?recursive=1).

### Inferences

- A same-origin proxy needs explicit server handlers before generic asset fallback and HTML injection, public worker/dependency delivery compatible with cold sessions, correct module/WASM MIME types, and deliberate header/cache rules. Dropping it under `public/apps/` alone is insufficient, especially since that directory is excluded in the current upload configuration. This is an untested implementation conclusion from the verified handler/configuration facts above. [Server](https://github.com/jo-jo-home/ojjys-game-hub/blob/91be48dcf75dbe7d1771eab9aa90b1b233c1a033/server.ts#L2722-L2868); [deno.json](https://github.com/jo-jo-home/ojjys-game-hub/blob/91be48dcf75dbe7d1771eab9aa90b1b233c1a033/deno.json).
- Route scopes organize worker control, but do not create origin-level separation from hub cookies/storage/APIs. A separate proxy origin is preferable for arbitrary rewritten content; a same-origin path would rely on the proxy sandbox and rewriting implementation. This is an architectural recommendation, not a demonstrated sandbox escape. [Hub session cookie](https://github.com/jo-jo-home/ojjys-game-hub/blob/91be48dcf75dbe7d1771eab9aa90b1b233c1a033/server.ts#L445-L448); [Scramjet architecture description](https://github.com/MercuryWorkshop/scramjet/blob/main/README.md); [worker same-origin requirement](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerContainer/register).

## 2. Can Deno Deploy host Wisp? What differs between Classic and the new platform?

### Takeaway

Do not claim that Deno Deploy categorically lacks outbound TCP or WebSockets: official docs support the relevant primitives. However, Classic explicitly prohibits raw TCP to port 443, and the current Deploy AUP lists forward proxies as unacceptable; standard Wisp hosting on Deploy is therefore not a supported recommendation merely because networking APIs exist. [Classic sockets](https://docs.deno.com/deploy/classic/api/runtime-sockets/); [TLS restriction](https://docs.deno.com/deploy/pricing_and_limits/#tls-proxying); [new runtime](https://docs.deno.com/deploy/reference/runtime/); [AUP](https://docs.deno.com/deploy/acceptable_use_policy/).

### Cited Findings

#### Classic — verified official documentation, not a target for a new build

- Classic supports outbound `Deno.connect` and `Deno.connectTls`. For `connect`, transport must be TCP and hostname cannot be localhost/empty; `connectTls` also disallows localhost/empty hostname. The API overview lists WebSocket and TCP/TLS APIs and describes outbound UDP as future support. [Classic socket reference](https://docs.deno.com/deploy/classic/api/runtime-sockets/); [Classic API overview](https://docs.deno.com/deploy/classic/api/).
- Crucial restriction: outgoing port 443 requires TLS termination. `Deno.connect` to 443 is prohibited; docs direct applications to `Deno.connectTls` instead. `fetch` is unaffected. The same page explicitly attributes the TLS-over-TLS proxy prohibition to Deploy Classic, despite living at an unqualified `/deploy/pricing_and_limits/` URL in the current navigation. Treat this statement as Classic-specific; it does not establish the same technical restriction for the new runtime. [Pricing/limitations, TLS proxying](https://docs.deno.com/deploy/pricing_and_limits/#tls-proxying).
- Classic documents Node module support including `http`, `net`, `tls`, `dns`, and `dgram`, with imperfect emulation and unavailable subprocess/worker/vm features. An importable module is not proof that every networking operation is supported. [Classic Node reference](https://docs.deno.com/deploy/classic/api/runtime-node/).
- Deno's current docs state that Classic and subhosting v1 were scheduled to shut down on July 20, 2026; new and Classic accounts/apps are separate and projects are not automatically transferred. Since research is dated after that date, this is strong reason not to plan a Classic deployment, but docs alone do not reveal the hub's actual migration history or live status. [Deploy comparison](https://docs.deno.com/deploy/); [migration guide](https://docs.deno.com/deploy/migration_guide/).

#### New Deno Deploy — verified official documentation

- The new platform runs the standard Deno runtime in isolated Linux environments with `--allow-all`, JSR/npm, filesystem writes, subprocesses, FFI, and native addons. The runtime page currently reports Deno 2.5.0 and says custom flags, including `--unstable-*`, cannot be passed. These are page-reported capabilities/version, not a runtime probe of the hub. [Runtime reference](https://docs.deno.com/deploy/reference/runtime/).
- WebSockets are supported in the documented lifecycle: active frames, including ping/pong, keep the app alive. Inactivity shutdown occurs after a variable 5-second to 10-minute interval. Active connections may still be interrupted by eviction; shutdown sends SIGINT, followed by forced SIGKILL after five seconds. Clients must reconnect. No fixed maximum Wisp session duration, guaranteed socket count, binary-frame size ceiling, or egress-port matrix was established from these pages. [Lifecycle](https://docs.deno.com/deploy/reference/runtime/#lifecycle).
- The standard `Deno.upgradeWebSocket(req)` API returns a WebSocket/Response pair and requires returning its upgrade response; reading the request body before upgrading makes the upgrade fail. The current API reference lists a default 30-second `idleTimeout`. These runtime API details must be checked against the deployed runtime version, rather than assuming every newest API option is in Deploy's page-reported 2.5.0. [WebSocket API](https://docs.deno.com/api/deno/websockets/#Deno.upgradeWebSocket).
- New Deploy uses apps/organizations and integrated builds, with configuration in the dashboard; CLI deployments use `deno deploy`, replacing `deployctl`. Migration requires `Deno.serve()` rather than legacy std HTTP `serve()`. The hub already uses the former; its `serveDir` import is a file-serving utility and is not that deprecated server startup function. [Migration](https://docs.deno.com/deploy/migration_guide/); [applications/build configuration](https://docs.deno.com/deploy/reference/apps/); [hub entrypoint](https://github.com/jo-jo-home/ojjys-game-hub/blob/91be48dcf75dbe7d1771eab9aa90b1b233c1a033/server.ts#L1670).
- Current AUP explicitly permits reverse proxies and disallows forward proxies and VPNs. A Wisp service exposing client-chosen destination host/port streams fits the forward-proxy use case as an architectural inference; full-runtime support does not establish permission to operate it. [AUP](https://docs.deno.com/deploy/acceptable_use_policy/); [Wisp CONNECT specification](https://github.com/MercuryWorkshop/wisp-protocol/blob/main/protocol.md).

#### Why Wisp differs from an HTTP fetch relay — verified upstream facts

- Wisp multiplexes destination TCP/UDP streams over one WebSocket. CONNECT names stream type, destination port, and hostname; DATA carries bytes for the destination stream. URLs should end in `/`, distinguishing Wisp from wsproxy-style endpoints. The inspected protocol v1.2 text calls UDP mandatory, while the current Scramjet example explicitly disables UDP; document a chosen TCP-only implementation as a deliberate subset rather than claiming complete v1.2 conformance. [Protocol](https://github.com/MercuryWorkshop/wisp-protocol/blob/main/protocol.md); [Scramjet server example](https://github.com/MercuryWorkshop/Scramjet-App/blob/f6f83cbc93091e47b9c357eb00ea289828aedf94/src/index.js).
- The Wisp project identifies libcurl.js as a browser WASM client performing HTTPS with full TLS encryption. The current Scramjet-App uses bare-mux plus `/libcurl/index.mjs` with a Wisp WebSocket URL. Consequently, normal HTTPS in this stack sends browser-generated TLS bytes through a raw destination TCP socket rather than asking the Wisp server to terminate destination TLS. [Wisp README](https://github.com/MercuryWorkshop/wisp-protocol/blob/main/README.md); [Scramjet transport initialization](https://github.com/MercuryWorkshop/Scramjet-App/blob/f6f83cbc93091e47b9c357eb00ea289828aedf94/public/index.js).
- `wisp-js` at observed HEAD `4fb68b0ea0644c06255ed023c0257eb6b9067825` uses `net.Socket()` for TCP destinations. Its `routeRequest(request, socket, head)` performs Node `WebSocketServer.handleUpgrade()` on a Node `IncomingMessage`. This is not the same call interface as `Deno.serve` receiving a Fetch `Request`. [TCP implementation](https://github.com/MercuryWorkshop/wisp-js/blob/4fb68b0ea0644c06255ed023c0257eb6b9067825/src/server/net.mjs); [HTTP upgrade implementation](https://github.com/MercuryWorkshop/wisp-js/blob/4fb68b0ea0644c06255ed023c0257eb6b9067825/src/server/http.mjs).

### Inferences

- **Classic HTTPS blocker:** replacing a Wisp destination's raw TCP socket with `connectTls()` is not a transparent solution. The client expects to perform its own TLS handshake; wrapping that byte stream in a second server-terminated TLS connection changes the protocol. Standard libcurl/epoxy Wisp HTTPS therefore conflicts with the documented Classic port-443 restriction. [TLS restriction](https://docs.deno.com/deploy/pricing_and_limits/#tls-proxying); [Wisp/browser TLS](https://github.com/MercuryWorkshop/wisp-protocol/blob/main/README.md).
- **New-runtime technical candidate, not a verified deployment:** Node-compatible Wisp may be technically plausible on the full runtime, but DNS, upgrade handling, binary frames, package compatibility, and connection lifecycle need a deployment proof. The existing hub's Fetch handler cannot call the Node upgrade function unchanged. The AUP remains the decisive documented hosting blocker. [New runtime](https://docs.deno.com/deploy/reference/runtime/); [wisp-js upgrade implementation](https://github.com/MercuryWorkshop/wisp-js/blob/4fb68b0ea0644c06255ed023c0257eb6b9067825/src/server/http.mjs); [AUP](https://docs.deno.com/deploy/acceptable_use_policy/).
- **Recommended backend:** run Wisp on a separate host with documented support for forward-proxy TCP egress and long-lived WebSockets. Let browsers connect directly to its `wss://.../wisp/` endpoint. Relaying Wisp through a Deno app would reintroduce that app into the forward-proxy data path, rather than solve the hosting-policy issue. This is a proposal grounded in Wisp's protocol and the current AUP, not a tested deployment. [Protocol](https://github.com/MercuryWorkshop/wisp-protocol/blob/main/protocol.md); [AUP](https://docs.deno.com/deploy/acceptable_use_policy/).

### Gaps

- **Actual deployment generation remains unknown.** `deploy.project` looks like legacy project-oriented configuration, but checked-in config is not the current dashboard. Need the live app URL, console/dashboard identification, build/runtime settings, and deployed revision to establish this. Neither the shutdown notice nor empty GitHub deployment/check data proves migration. [Hub configuration](https://github.com/jo-jo-home/ojjys-game-hub/blob/91be48dcf75dbe7d1771eab9aa90b1b233c1a033/deno.json); [migration guide](https://docs.deno.com/deploy/migration_guide/).
- New Deploy's exact raw-443 behavior was not tested and no new-platform-specific technical ban was established. Do not copy the Classic ban to the new platform as fact, and do not interpret absence of that ban as permission to host Wisp. [Classic-specific statement](https://docs.deno.com/deploy/pricing_and_limits/#tls-proxying); [new runtime](https://docs.deno.com/deploy/reference/runtime/); [AUP](https://docs.deno.com/deploy/acceptable_use_policy/).
- A frontend-only Scramjet/UV app on Deploy, while Wisp is external, is technically distinct from server-side forwarding. Whether Deno considers that broader application acceptable is not resolved by the cited pages; no provider-specific determination was obtained.
- No Wisp backend was selected, deployed, or load-tested; no WebSocket/TCP/TLS probes were performed. Exact capacity, costs, reconnect behavior, DNS implementation, and browser transport compatibility remain unverified.

## 3. What standalone-first architecture and later hub integration should be built?

### Takeaway

Build a standalone proxy frontend on its own HTTPS origin with an external Wisp backend first. Later add a hub launcher route/card that opens that origin as a top-level page; same-origin proxy mounting is a secondary, untested option requiring explicit worker exclusions and route/header handling. [Upstream app architecture](https://github.com/MercuryWorkshop/Scramjet-App/blob/f6f83cbc93091e47b9c357eb00ea289828aedf94/src/index.js); [browser scope rules](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerContainer/register); [hub worker](https://github.com/jo-jo-home/ojjys-game-hub/blob/91be48dcf75dbe7d1771eab9aa90b1b233c1a033/public/sw.js).

### Cited Findings

- Scramjet describes itself as experimental. UV's current README says it is no longer really maintained and has been superseded by Scramjet; UV v3 uses bare-mux. This supports Scramjet as the default engine and UV as an explicitly labeled fallback, rather than treating both as equally maintained. [Scramjet README](https://github.com/MercuryWorkshop/scramjet/blob/main/README.md); [UV README](https://github.com/titaniumnetwork-dev/Ultraviolet/blob/main/README.md).
- Scramjet-App at observed HEAD `f6f83cbc93091e47b9c357eb00ea289828aedf94` serves `/scram/`, `/libcurl/`, `/baremux/`, registers `./sw.js`, and sets `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy: require-corp` on HTTP responses. Its worker calls `loadConfig()`, checks `scramjet.route(event)`, then fetches through Scramjet or the network. These are reference application defaults, not hub-compatible prefixes without modification. [Server](https://github.com/MercuryWorkshop/Scramjet-App/blob/f6f83cbc93091e47b9c357eb00ea289828aedf94/src/index.js); [registration](https://github.com/MercuryWorkshop/Scramjet-App/blob/f6f83cbc93091e47b9c357eb00ea289828aedf94/public/register-sw.js); [worker](https://github.com/MercuryWorkshop/Scramjet-App/blob/f6f83cbc93091e47b9c357eb00ea289828aedf94/public/sw.js).
- The UV-Static config uses `prefix: "/uv/service/"` and points to `/uv/uv.handler.js`, `/uv/uv.client.js`, `/uv/uv.bundle.js`, `/uv/uv.config.js`, and `/uv/uv.sw.js`. These paths would all need relocation for a namespaced hub build. [UV config](https://github.com/titaniumnetwork-dev/Ultraviolet-Static/blob/main/public/uv/uv.config.js).
- Browser registration requires same-origin script/scope and a trustworthy context, and worker scripts need valid JavaScript MIME. Default scope is the script's directory; the most specific matching registration controls a document, with only one controlling worker per document. A second root registration updates/replaces the existing root registration rather than layering another worker. [MDN register](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerContainer/register).
- COOP/COEP and Permissions-Policy determine `crossOriginIsolated`; isolated pages can use SharedArrayBuffer and related APIs. The current hub doesn't supply these headers in its common HTML header map. The upstream libcurl setup does supply them, so isolation must be verified for the chosen transport, not assumed for all Scramjet configurations. [MDN isolation](https://developer.mozilla.org/en-US/docs/Web/API/Window/crossOriginIsolated); [hub headers](https://github.com/jo-jo-home/ojjys-game-hub/blob/91be48dcf75dbe7d1771eab9aa90b1b233c1a033/server.ts#L110-L116); [upstream server headers](https://github.com/MercuryWorkshop/Scramjet-App/blob/f6f83cbc93091e47b9c357eb00ea289828aedf94/src/index.js).

### Inferences

#### Stage A — standalone initial build (all items are untested proposals)

1. **Origins:** use a dedicated `https://proxy.<owned-domain>` frontend origin and a separate `wss://relay.<owned-domain>/wisp/` backend, or colocate those services on one non-Deploy host that permits the use case. These names are placeholders, not provisioned domains. Own-origin frontend delivery avoids the hub worker and its auth-cookie/storage namespace. Keep transport configuration explicitly pointing at external Wisp rather than deriving it from `location.host` as the upstream demo does. [Demo transport](https://github.com/MercuryWorkshop/Scramjet-App/blob/f6f83cbc93091e47b9c357eb00ea289828aedf94/public/index.js); [hub worker registration](https://github.com/jo-jo-home/ojjys-game-hub/blob/91be48dcf75dbe7d1771eab9aa90b1b233c1a033/public/offline.js).
2. **Reserve a portable namespace from day one:** `/proxy/` shell, `/proxy/assets/scramjet/`, `/proxy/assets/uv/`, `/proxy/assets/baremux/`, `/proxy/assets/libcurl/`, and virtual URL prefixes `/proxy/scramjet/` and `/proxy/ultraviolet/`. Serve one dispatcher at `/proxy/sw.js`, registered explicitly for `/proxy/`, dispatching only the corresponding engine prefixes and passing other requests to the network. Scramjet config and UV's `prefix`/file paths must match this map. There is no need for `Service-Worker-Allowed: /` with this placement. This combined engine dispatcher has not been implemented or verified. [Scramjet dispatcher example](https://github.com/MercuryWorkshop/Scramjet-App/blob/f6f83cbc93091e47b9c357eb00ea289828aedf94/public/sw.js); [UV path config](https://github.com/titaniumnetwork-dev/Ultraviolet-Static/blob/main/public/uv/uv.config.js); [scope rules](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerContainer/register).
3. **Transport and engine selection:** default to Scramjet, provide UV fallback only after verifying its selected version with the same bare-mux/Wisp transport. Pin engine/transport distributions together, bundle JS/WASM locally at frontend build time, and use independent proxy cache names. Do not infer supported-site guarantees from README lists. [UV maintenance/bare-mux](https://github.com/titaniumnetwork-dev/Ultraviolet/blob/main/README.md); [Scramjet frontend dependency paths](https://github.com/MercuryWorkshop/Scramjet-App/blob/f6f83cbc93091e47b9c357eb00ea289828aedf94/public/index.js).
4. **Headers/cache delivery:** follow the selected transport's COOP/COEP requirements on the proxy shell and verify `crossOriginIsolated`. Worker/config responses should revalidate or be non-cached as appropriate; fingerprinted compatible asset bundles can be immutable. Serve `.js`/`.mjs` as JavaScript and WASM as `application/wasm`; avoid redirecting worker/dependency requests to a login page. Ordinary rewritten target browsing should not enter the hub offline download catalogue. [Upstream headers](https://github.com/MercuryWorkshop/Scramjet-App/blob/f6f83cbc93091e47b9c357eb00ea289828aedf94/src/index.js); [MDN isolation](https://developer.mozilla.org/en-US/docs/Web/API/Window/crossOriginIsolated); [worker MIME rules](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerContainer/register).

#### Stage B — preferred hub integration: launcher plus separate origin

- Add an authenticated hub entry such as `/proxy` or a proxy app card that opens the standalone `https://proxy.<owned-domain>/proxy/` page directly, as a top-level navigation/new tab. That route is a launcher, not a forward-proxy endpoint. Keep the actual worker/bundles/virtual URLs on the proxy origin; keep Wisp on the external backend. The root hub worker cannot control that other origin. [Hub generated page pattern](https://github.com/jo-jo-home/ojjys-game-hub/blob/91be48dcf75dbe7d1771eab9aa90b1b233c1a033/server.ts#L2722-L2815); [same-origin worker rules](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerContainer/register).
- A hub link is UI integration, not shared authentication. The host-only hub cookie will not automatically authenticate a sibling proxy host. Start with independent access semantics; any later SSO handoff needs its own explicit design rather than forwarding the long-lived hub `?token=` to another origin. [Cookie implementation](https://github.com/jo-jo-home/ojjys-game-hub/blob/91be48dcf75dbe7d1771eab9aa90b1b233c1a033/server.ts#L445-L448); [hub token behavior](https://github.com/jo-jo-home/ojjys-game-hub/blob/91be48dcf75dbe7d1771eab9aa90b1b233c1a033/server.ts#L1721-L1733).
- Prefer direct top-level launch initially over the hub's about:blank wrapper/iframe. Isolation headers and COEP resource requirements can interact with embedding, while the existing wrapper relies on special session propagation. Embedding compatibility remains a browser test, not an assumed requirement or an assumed impossibility. [Isolation semantics](https://developer.mozilla.org/en-US/docs/Web/API/Window/crossOriginIsolated); [existing launcher](https://github.com/jo-jo-home/ojjys-game-hub/blob/91be48dcf75dbe7d1771eab9aa90b1b233c1a033/server.ts#L2792-L2815).

#### Stage C — optional same-origin mount, if later required

- Redirect bare `/proxy` to `/proxy/`, since the trailing-slash namespace is what the proposed worker controls. Retain `/proxy/sw.js` with scope `/proxy/`; never transplant the upstream demo's root `/sw.js` over the hub's worker. Most-specific scope lets the proxy registration coexist with the root worker, but its initial uncontrolled loads and requests from hub-controlled clients still require care. [Scope matching](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerContainer/register); [hub root worker](https://github.com/jo-jo-home/ojjys-game-hub/blob/91be48dcf75dbe7d1771eab9aa90b1b233c1a033/public/sw.js).
- The hub root worker should explicitly ignore `/proxy` and `/proxy/*`, including virtual URLs, configuration, and bundles, before its navigation/asset caching logic. Scope determines which worker controls a document, not a universal URL-based firewall for all fetches by that document. Wait for the proxy worker to activate/control before navigating to virtual URLs. Do not unregister the hub root worker or delete `hub-games-v1`. [Hub fetch logic](https://github.com/jo-jo-home/ojjys-game-hub/blob/91be48dcf75dbe7d1771eab9aa90b1b233c1a033/public/sw.js#L248-L272); [scope rules](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerContainer/register).
- Add dedicated proxy handlers for packaged worker/dependencies before the generic auth/static fallback; apply shell authentication separately, and avoid hub head injection. Apply isolation headers to the proxy namespace rather than globally to all game pages. Ensure fresh clients requesting virtual URLs get a deliberate bootstrap/error behavior instead of accidental GitHub fallback. Keep external Wisp connectivity; hosting frontend assets on the hub does not establish permission to add a Wisp backend. [Hub routing/injection](https://github.com/jo-jo-home/ojjys-game-hub/blob/91be48dcf75dbe7d1771eab9aa90b1b233c1a033/server.ts#L2722-L2868); [upstream isolation](https://github.com/MercuryWorkshop/Scramjet-App/blob/f6f83cbc93091e47b9c357eb00ea289828aedf94/src/index.js); [AUP](https://docs.deno.com/deploy/acceptable_use_policy/).
- Package proxy assets in the actual deployment output, pin dependency versions, and explicitly map `.mjs`. Do not rely on `public/apps` surviving existing exclusions or on moving GitHub master to provide a compatible worker/bundle set. Same-origin path separation still does not separate hub credentials/storage from proxy code. [Deploy exclusions](https://github.com/jo-jo-home/ojjys-game-hub/blob/91be48dcf75dbe7d1771eab9aa90b1b233c1a033/deno.json); [fallback MIME/cache](https://github.com/jo-jo-home/ojjys-game-hub/blob/91be48dcf75dbe7d1771eab9aa90b1b233c1a033/server.ts#L2817-L2842); [cookie scope](https://github.com/jo-jo-home/ojjys-game-hub/blob/91be48dcf75dbe7d1771eab9aa90b1b233c1a033/server.ts#L445-L448).

### Gaps

- **Blocking hosting decision:** select a Wisp host whose supported use case includes forward-proxy TCP egress. Current Deno Deploy docs are insufficient grounds for recommending Wisp there, and the AUP gives a direct reason against it. [AUP](https://docs.deno.com/deploy/acceptable_use_policy/).
- **Blocking deployment inventory:** obtain the hub's live URL and current platform/build configuration before preparing a hub-side implementation. Repository configuration suggests historical Classic usage but cannot identify the actual serving generation. [Configuration](https://github.com/jo-jo-home/ojjys-game-hub/blob/91be48dcf75dbe7d1771eab9aa90b1b233c1a033/deno.json); [migration model](https://docs.deno.com/deploy/migration_guide/).
- **Unverified browser/engine behavior:** combined Scramjet/UV worker routing, controller takeover, transport versions, WASM loading, real HTTPS requests, target WebSockets, disconnect recovery, login/logout and browsing storage isolation have not been tested. Validate standalone first, then test hub integration with a pre-existing root worker and saved offline games.
- **Unverified embedding:** test normal top-level launch before iframe/about:blank integration, including `crossOriginIsolated`, COEP response behavior, worker registration, managed-browser restrictions, and cookies. No claim of successful embedding is made. [Isolation requirements](https://developer.mozilla.org/en-US/docs/Web/API/Window/crossOriginIsolated); [existing launcher/session context](https://github.com/jo-jo-home/ojjys-game-hub/blob/91be48dcf75dbe7d1771eab9aa90b1b233c1a033/server.ts#L1721-L1733).
- **Source scope:** upstream files were fetched from their current default branches; Scramjet-App and wisp-js observed HEAD SHAs are recorded above for reproducibility. Other upstream/official-doc links are rolling sources and should be rechecked before implementation. No application builds, test runs, live route probes, edits, commits, or deployments were performed in this research task.
