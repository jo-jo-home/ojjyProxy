# ojjyProxy networking: Scramjet, Ultraviolet, Epoxy and relay deployment

Research date: 2026-10-12. Evidence consists of upstream documentation/source and read-only inspection of the six requested ZIPs using Python `zipfile`; no archives were extracted, no dependencies installed, and no proxy runtime or browser compatibility tests performed. “Compatible” below means a source-integrated, lockfile-resolved combination, not a newly tested deployment. Local citations identify ZIP/member paths; commit-pinned GitHub links provide corresponding upstream source locations. Live branch references can move.

## 1. What belongs in the networking architecture, and how do Wisp and Bare differ?

### Takeaway
Use a Wisp relay with Epoxy as the default network transport. For the requested dual-engine design, retain bare-mux for Ultraviolet's legacy interface while treating modern Scramjet's directly supplied `ProxyTransport` as a separate integration path; bare-mux is now explicitly deprecated upstream.

### Cited Findings
- Scramjet/Ultraviolet are page-rewriting engines, rather than interchangeable names for the relay. bare-mux manages HTTP transports and implements a modular TompHTTP Bare client interface. Its README explicitly says it is deprecated and directs users to `proxy-transports`; v2 uses SharedWorkers. Thus “BareClient” or “BareMuxConnection” in browser code does **not** establish that a Bare protocol server is needed. — [bare-mux README](https://raw.githubusercontent.com/MercuryWorkshop/bare-mux/master/README.md)
- `proxy-transports` is the successor interface for HTTPS/WSS transports. Its `request()` uses `RawHeaders`; `connect()` supplies both protocol and extensions in the open callback. This differs from the older bare-mux interface shown in its README, so replacing packages alone is not a migration. — [successor README](https://raw.githubusercontent.com/MercuryWorkshop/proxy-transports/master/README.md); [older interface](https://raw.githubusercontent.com/MercuryWorkshop/bare-mux/master/README.md)
- Epoxy runs TLS inside browser WebAssembly and uses Wisp to proxy TCP connections. The browser library exposes fetch, WebSocket, and lower-level stream capabilities. `epoxy-transport` adapts that library into a proxy transport; its current README demonstrates `new EpoxyClient({ wisp: "wss://example.com/wisp/" })`. — [Epoxy repository](https://github.com/MercuryWorkshop/epoxy-tls); [client usage](https://raw.githubusercontent.com/MercuryWorkshop/epoxy-tls/multiplexed/client/README.md); [transport usage](https://raw.githubusercontent.com/MercuryWorkshop/Epoxy-Transport/master/README.md)
- Wisp multiplexes multiple TCP sockets over one WebSocket; its repository lists Python, JavaScript, Rust and C++ implementations. Implementations and negotiated extensions must be distinguished from the protocol specification. — [Wisp upstream](https://raw.githubusercontent.com/MercuryWorkshop/wisp-protocol/main/README.md)
- A Bare backend is a separate TompHTTP implementation, with CLI and programmatic Node server APIs. It is not the backend protocol used by an Epoxy/Wisp transport. bare-mux lists a Bare client transport alongside Epoxy and curl transports. — [Bare server](https://raw.githubusercontent.com/tomphttp/bare-server-node/master/README.md); [transport alternatives](https://raw.githubusercontent.com/MercuryWorkshop/bare-mux/master/README.md)
- Upstream Ultraviolet 3.2.10 depends on bare-mux `^2.1.7`; the inspected production snapshot integrates UV through a `BareMuxConnection`, but constructs a separate transport instance for Scramjet's `Controller`, explicitly awaiting `transport.init()`. Both receive the same Wisp endpoint/options, but are not demonstrably sharing one underlying connection. — [UV manifest](https://raw.githubusercontent.com/titaniumnetwork-dev/Ultraviolet/master/package.json); [production registration code](https://github.com/InvisiProxy/InvisiProxyLTS/blob/eac37e3ea3f61406e6b2eaad79eef4feb38c476d/views/assets/js/register-sw.js)
- The Epoxy showcase URL was reachable, but returned an HTML/JavaScript application shell, not readable technical documentation or a successful live transport test. The authoritative technical findings here come from its linked upstream sources. — [showcase](https://epoxy.r58playz.dev/)

### Inferences
- Recommended conceptual flow:

  ```text
  browser shell / engine choice
    ├─ Ultraviolet 3.x service worker → bare-mux 2.x worker → compatible transport
    └─ Scramjet 2.x controller/service worker → initialized ProxyTransport
                                                    ↓
                                Epoxy HTTPS/TLS in browser WASM
                                                    ↓
                                    wss://own-host/wisp/
                                                    ↓
                              Wisp relay → destination TCP socket
  ```

  This is inferred from the inspected dual-engine registration and upstream APIs. Use the production branch's header-compatible UV artifact for that particular Epoxy 3 pairing rather than assuming stock UV and every transport major interoperate. — [production code](https://github.com/InvisiProxy/InvisiProxyLTS/blob/eac37e3ea3f61406e6b2eaad79eef4feb38c476d/views/assets/js/register-sw.js); [production dependency manifest](https://github.com/InvisiProxy/InvisiProxyLTS/blob/eac37e3ea3f61406e6b2eaad79eef4feb38c476d/package.json)
- With destination HTTPS and certificate verification enabled, browser-side TLS makes the relay an encrypted byte forwarder rather than the HTTPS terminator. It does not imply anonymity: the relay still handles destination information and timing, plaintext HTTP is not destination-encrypted, and a compromised shell supplying the JS/WASM remains within the trust boundary. These are architectural deductions, not independently audited privacy guarantees. — [Epoxy architecture](https://github.com/MercuryWorkshop/epoxy-tls); [Wisp description](https://raw.githubusercontent.com/MercuryWorkshop/wisp-protocol/main/README.md)
- Bare is useful only as an explicitly chosen alternate transport/backend pair. Adding a Bare server will not fix an unavailable Wisp endpoint when Epoxy is selected. For a Bare HTTP relay, destination TLS normally resides at the relay, unlike Epoxy's browser-side TLS; the specific implementation's trust model should be reviewed before offering it as a fallback. — [Bare implementation](https://raw.githubusercontent.com/tomphttp/bare-server-node/master/README.md); [Epoxy description](https://github.com/MercuryWorkshop/epoxy-tls)
- Keep transport selection and engine selection separate. A libcurl transport can be an alternative Wisp-backed HTTP/TLS implementation without switching the rewrite engine. Shared endpoint configuration is reusable; shared connection state across the two integration paths should not be promised. — [production initialization](https://github.com/InvisiProxy/InvisiProxyLTS/blob/eac37e3ea3f61406e6b2eaad79eef4feb38c476d/views/assets/js/register-sw.js)

### Gaps
- No tested browser matrix, connection-pooling measurements, benchmarks, or end-to-end privacy audit was obtained. SharedWorker availability, private-mode behavior, WASM startup and reconnect behavior need runtime verification.
- The fetched Bare README establishes the implementation/API but does not by itself validate detailed TLS or license behavior for a chosen release.

## 3. Which backend and deployment pattern should ojjyProxy use, and what are the practical limits?

### Takeaway
Prefer one HTTPS origin serving the frontend plus a persistent `/wisp/` WebSocket route. A plain Node Wisp implementation is simplest to integrate; Wispurr offers Go worker processes and operational controls; Rust epoxy-server is a separate service option. Choose by operational needs rather than undocumented throughput claims.

### Cited Findings

#### Backend choices

| Backend | Verified capabilities / deployment | Fit and qualifications | Source |
|---|---|---|---|
| `@mercuryworkshop/wisp-js` | Node/browser library, v1/v2, standalone CLI or `server.on("upgrade", ...)` + `routeRequest`; server defaults localhost:5001; DNS, destination and stream controls | Lowest language/toolchain complexity for a Node app; no independently measured performance comparison | [README](https://raw.githubusercontent.com/MercuryWorkshop/wisp-js/master/README.md) |
| `wispurr` | Go server plus Node wrapper; Wisp v1/v2, optional UDP/Twisp, upstream proxy, authentication, egress policy, real-IP parsing, limits/flood controls; wrapper spawns and load-balances workers; source requires Go 1.25+ | Matches current InvisiProxy integration; adds worker processes/binary platform considerations | [README](https://raw.githubusercontent.com/sylvieisnton/wispurr/main/README.md) |
| `epoxy-server` | Rust Wisp server; `cargo b -r`; config path argument; TOML/JSON/YAML documentation; `--default-config` and `--format` | Separate persistent process; client does not inherently require this particular implementation | [server README](https://raw.githubusercontent.com/MercuryWorkshop/epoxy-tls/multiplexed/server/README.md) |
| `wisp-server-python` / `wisp-python` | Python v1 implementation including UDP; CLI, threads on Linux, upstream proxy and connection/bandwidth limits; recommends CPython >=3.11 | Useful separately operated relay; v2 remains in README roadmap, so do not assume parity with v2 backends | [README](https://raw.githubusercontent.com/MercuryWorkshop/wisp-server-python/main/README.md) |
| TompHTTP Bare Node | CLI and programmatic Bare server | Only needed for a chosen Bare-compatible client transport; not an Epoxy relay | [README](https://raw.githubusercontent.com/tomphttp/bare-server-node/master/README.md) |

- The generic `MercuryWorkshop/wisp-server` raw README paths checked returned 404. Upstream's verified protocol README instead points to `wisp-server-python`, `wisp-js/server`, epoxy-server and Woeful; this research uses those concrete implementations rather than treating “wisp-server” as one current package. — [implementation list](https://raw.githubusercontent.com/MercuryWorkshop/wisp-protocol/main/README.md)
- Epoxy's client example enables Wisp v2 and requires the UDP extension. It labels the public demo relay throttled and recommends self-hosting. A TCP-only relay configuration must not be paired blindly with that example's required-UDP setting. — [client README](https://raw.githubusercontent.com/MercuryWorkshop/epoxy-tls/multiplexed/client/README.md)
- InvisiProxy master starts one Wispurr worker, awaits startup, routes matching HTTP upgrades, destroys unmatched sockets, and stops workers on shutdown. Its relay configuration binds to 127.0.0.1:4432, enables TCP/v2, disables UDP/Twisp/direct-IP/private-IP/loopback-IP connections, and blocks SMTP ports 25/465/587. — [server lifecycle](https://github.com/InvisiProxy/InvisiProxyLTS/blob/242386f1d01b778a563cafe54567f5b832a6f7cf/src/server/index.ts); [relay configuration](https://github.com/InvisiProxy/InvisiProxyLTS/blob/242386f1d01b778a563cafe54567f5b832a6f7cf/src/server/wisp.ts)

#### Deployment evidence and documentation conflicts

- Client registration derives `ws` versus `wss` from the page scheme, uses the page host and configured Wisp path, and requires HTTPS except localhost/127.0.0.1 for service workers. Production registers separate SJ/UV scopes. Master serves a `Service-Worker-Allowed` response header for its base path. — [production registration](https://github.com/InvisiProxy/InvisiProxyLTS/blob/eac37e3ea3f61406e6b2eaad79eef4feb38c476d/views/assets/js/register-sw.js); [master HTTP handler](https://github.com/InvisiProxy/InvisiProxyLTS/blob/242386f1d01b778a563cafe54567f5b832a6f7cf/src/server/handler.ts)
- NGINX requires explicitly forwarded `Upgrade`/`Connection` headers for WebSocket proxying. Its documentation notes a default 60-second inactivity timeout and suggests increasing `proxy_read_timeout` or sending periodic WebSocket pings; HTTP/1.1 must be explicitly configured on versions before 1.29.7. — [NGINX documentation](https://nginx.org/en/docs/http/websocket.html)
- Inspected master, production, soap and soap-rewrite Dockerfiles use `node:26-alpine`, install Tor/build dependencies, enable Corepack with `pnpm@latest`, and expose 8080/9050/9051. Their Compose files publish only 8080. Dev uses `node:20-alpine` and npm. Production's manifest says 7.0.2.1 while Docker metadata/image selection says 7.0.2. — [master Dockerfile](https://github.com/InvisiProxy/InvisiProxyLTS/blob/242386f1d01b778a563cafe54567f5b832a6f7cf/Dockerfile); [production Dockerfile](https://github.com/InvisiProxy/InvisiProxyLTS/blob/eac37e3ea3f61406e6b2eaad79eef4feb38c476d/Dockerfile); [production Compose](https://github.com/InvisiProxy/InvisiProxyLTS/blob/eac37e3ea3f61406e6b2eaad79eef4feb38c476d/docker-compose.yml); [dev Dockerfile](https://github.com/InvisiProxy/InvisiProxyLTS/blob/4482b3cbc3387c2de1209d5bf3832688ca000534/Dockerfile)
- Master declares Node >=24, targets Node 24 in its build, and uses TypeScript/Vite native config loading. The README nevertheless contains Node 20 instructions and a Node 26 example, old config filenames, and references to UV no longer present in master. ### Inferences

#### Practical recommended pattern

1. **Single origin:** terminate HTTPS at NGINX and serve frontend/worker/transport assets through that origin. Route `/wisp/` upgrades to a persistent Node app or a dedicated Wisp process. Keep the endpoint's trailing slash and any deployment base path aligned with the client and upgrade matcher. Explicitly forward WebSocket headers and accommodate long-lived idle connections. — [registration](https://github.com/InvisiProxy/InvisiProxyLTS/blob/eac37e3ea3f61406e6b2eaad79eef4feb38c476d/views/assets/js/register-sw.js); [upgrade routing](https://github.com/InvisiProxy/InvisiProxyLTS/blob/242386f1d01b778a563cafe54567f5b832a6f7cf/src/server/index.ts); [NGINX](https://nginx.org/en/docs/http/websocket.html)
2. **Backend selection:** choose wisp-js for simple in-process Node operation; choose Wispurr when its binary/worker management and operational controls are useful; choose Rust/Python as separately managed services when those environments are preferred. Protocol compatibility and required extensions determine whether a swap works, not the rewrite engine's name. — [wisp-js API](https://raw.githubusercontent.com/MercuryWorkshop/wisp-js/master/README.md); [Wispurr wrapper](https://raw.githubusercontent.com/sylvieisnton/wispurr/main/README.md); [Epoxy client options](https://raw.githubusercontent.com/MercuryWorkshop/epoxy-tls/multiplexed/client/README.md)
3. **Reproducible deployment:** pin Node, package manager, dependency lock and image digest; install the reviewed lock without an update step; build assets once and retain matched JS/WASM/controller artifacts. The source templates' `latest` package-manager activation and update-first scripts are lessons to improve, not reproducibility examples. — [Dockerfile](https://github.com/InvisiProxy/InvisiProxyLTS/blob/242386f1d01b778a563cafe54567f5b832a6f7cf/Dockerfile); [manifest scripts](https://github.com/InvisiProxy/InvisiProxyLTS/blob/242386f1d01b778a563cafe54567f5b832a6f7cf/package.json)
4. **Destination policy:** borrow master's private/loopback restrictions and deliberate trusted-proxy configuration rather than blindly copying production's enabled loopback. Tor/SOCKS routing needs a deliberately chosen backend/transport topology: browser option `localhost:9050` is interpreted by the proxy implementation, not a Tor daemon running on the visitor's computer. Backend-level upstream-proxy settings can be clearer than permitting arbitrary clients to dial relay-local services. — [master policy](https://github.com/InvisiProxy/InvisiProxyLTS/blob/242386f1d01b778a563cafe54567f5b832a6f7cf/src/server/wisp.ts); [Wispurr upstream proxy capability](https://raw.githubusercontent.com/sylvieisnton/wispurr/main/README.md); [client options](https://github.com/InvisiProxy/InvisiProxyLTS/blob/242386f1d01b778a563cafe54567f5b832a6f7cf/views/assets/js/register-sw.js)
5. **Split hosting:** a static frontend plus a separate WSS relay is architecturally possible; soap's configurable Wisp URL is a concrete reuse reference. A static-only host cannot itself supply the persistent outbound-socket relay. A serverless offering needs explicit support for long-lived WebSockets and required outbound networking, rather than reliance on a deploy button. — [soap endpoint resolver](https://github.com/InvisiProxy/InvisiProxyLTS/blob/ea4b86287b209c78d0c4e8138994b63a19e7a1bb/views/assets/js/register-sw.js); [Wisp architecture](https://raw.githubusercontent.com/MercuryWorkshop/wisp-protocol/main/README.md)

#### Limits to preserve in implementation planning

- Wisp is socket forwarding, not a universal browser-network virtualization layer. A TCP/HTTP transport and rewritten page do not establish support for WebRTC, QUIC/HTTP3, DRM, every browser API or every CAPTCHA. Current inspected InvisiProxy configurations explicitly disable UDP. — [master configuration](https://github.com/InvisiProxy/InvisiProxyLTS/blob/242386f1d01b778a563cafe54567f5b832a6f7cf/src/server/wisp.ts); [CAPTCHA caveat](https://github.com/InvisiProxy/InvisiProxyLTS)
- Multiplexing reduces the number of outer sockets but also couples streams to one WebSocket failure and its underlying TCP behavior; reconnect, mobile sleep and streaming cancellation need measurement. This is an inference from multiplexing, not a benchmark result. — [protocol overview](https://raw.githubusercontent.com/MercuryWorkshop/wisp-protocol/main/README.md)
- Validate cold start, service-worker replacement/scope, WASM asset loading, POST/redirect/cookies/raw headers, streaming, destination WSS, transport changes, relay restart/idle timeout, IPv4/IPv6 policy and proxy-header handling before calling a combination production-ready. The production branch's name and package presence do not constitute these tests. — [initialization/error handling](https://github.com/InvisiProxy/InvisiProxyLTS/blob/eac37e3ea3f61406e6b2eaad79eef4feb38c476d/views/assets/js/register-sw.js); [NGINX timeout](https://nginx.org/en/docs/http/websocket.html); [relay settings](https://github.com/InvisiProxy/InvisiProxyLTS/blob/242386f1d01b778a563cafe54567f5b832a6f7cf/src/server/wisp.ts)

### Gaps
- No deployment was performed; Go binary availability for a selected package/platform, Alpine behavior, memory/CPU/bandwidth use, worker scaling and load-balancer behavior remain unmeasured.
- No current provider pricing, proxy policy, free-tier support or WebSocket duration limits were independently verified. README deploy badges are not evidence of working contemporary hosting.
- No generic throughput winner is supportable from the fetched sources. Epoxy-server's performance wording and Wispurr's operational feature list are not comparative measurements.
- The supplied showcase was fetched but not executed. No live Epoxy fetch, certificate-validation test, public relay health check or headers-tarball runtime compatibility check was performed.
